# NereusSDR for iPhone and iPad: Implementation Plan

> **Execution:** run with `crew` (`/crew <this file>`) under `cost-aware-execution`.
> Requirements and acceptance cases are binding; test order and review effort follow
> the risk-based policy; UI evidence follows `ui-verification`. Two sessions run this
> one plan, each only its own tasks (Global Constraints, "Who runs which task"). No
> review between tasks; each session ends with one whole-branch review of its branch.

**Goal:** Ship the NereusSDR iPhone and iPad app, with receive and transmit in the first
App Store release, together with every station, desktop and service change it needs, as
one body of work.

**Architecture:** The station (`nereusd`, or the desktop app while it is open) does all
radio and DSP work and speaks one written, versioned link: a TLS WebSocket control
session carrying JSON, plus WebRTC media (Opus audio, NSDC display frames). This plan
writes that link down with a conformance suite both ends run, then gives the station
per-device identity and pairing; the values, lists, Setup descriptions and ported display
computations the phone shows; remote access through a rendezvous and relay; remote
transmit with its whole safety harness (starting with the DSP-control thread R-R3-39
requires); the takeover question and the transmit-coupled accessory commands; and the
desktop's station switch. The app is a Swift package (`NereusKit`: link, mirror, media,
band) that builds and tests on macOS, plus a SwiftUI and Metal app with a Live Activity
extension, generated by XcodeGen.

**Tech Stack:** Station and desktop: C++20, Qt 6 (Core, Network, WebSockets, Widgets,
Test), CMake and Ninja, OpenSSL 3, libdatachannel 0.24.5 with libjuice, libsrtp and
usrsctp, Opus, libsodium and SPAKE2+EE (new), coturn (server side only). App: Swift 6.3
(6.4 with Xcode 27), SwiftUI, Metal, Network framework, AVFAudio, ActivityKit,
PushToTalk, CoreBluetooth, CryptoKit, swift-testing, XcodeGen; vendored C sources for
Opus, libdatachannel, libjuice, libsrtp, usrsctp, Mbed TLS, libsodium and SPAKE2+EE.

**Spec:** [2026-09-23-iphone-app-design.md](2026-09-23-iphone-app-design.md). Every
decision is settled there (D1 to D42, requirements R-IOS-01 to R-IOS-29); this is how it
gets built. The station documents it cites (the remote design, the pairing design, the
R3 plan, media control, the display codec, notch control) are on `codex/integrate-r2-main`,
read for this plan at `4bb89b5d`.

## Global Constraints

* **Design authority** is the spec, plus, for the station, the remote design
  (`2026-07-28-remote-daemon-architecture-design.md`), the pairing design
  (`2026-08-02-remote-station-identity-and-pairing-design.md`) and the R3 plan
  (`2026-09-20-remote-daemon-r3-plan.md`). Do not relitigate a decision. If the spec is
  wrong or silent on something material, stop and report NEEDS_CONTEXT.
* **Who runs which task** (JJ's decision, 2026-09-24): one plan, one owner per task,
  and each task opens with a **Runs in** line that says which.
  * **Station tasks** (1 to 4, 12 to 14, and 16 to 50 without the lettered ones) run in
    the Core/GUI session's lanes and reach `codex/integrate-r2-main`. Their build
    directory is the lane's (`build-integration` or `build-lane-b`), and `build` in a
    verification command means that directory.
  * **Phone tasks** (5 to 11, 15, 16a, 27a, 28a, 29a, 51 to 69, and 70 with JJ) run in
    the phone session on `claude/iphone-app`, cut from `codex/integrate-r2-main` (see
    "Before Task 1"). Its controller merges `codex/integrate-r2-main` into
    `claude/iphone-app` only between tasks and never commits to
    `codex/integrate-r2-main`.
  * A phone task starts only when every station task it consumes has reached
    `codex/integrate-r2-main` and been merged in. Until then it waits, and the controller
    tells JJ which station task it is waiting on; nothing stands in for a missing piece.
  * Each controller's ledger records the other session's tasks as they land
    (`Task N: complete (<session>, <commit>)`) and skips every task it does not own.
  * This plan and its spec change only on `claude/nereussdr-iphone-app-5fb988`, whose
    copy is the authority; the Core/GUI session cherry-picks each plan commit into its
    lanes. Before a station task changes anything a phone task reads (the
    `tests/data/link/v1/` layout, `surface.json`'s top-level keys, `hello`'s `majors`
    and `features`, the version rule), the Core/GUI session tells the phone session.
* **The other agent.** Another agent works in `/Users/j.j.boyd/.codex/`; never open or
  change anything there.
* **Tracing.** Every commit names the requirement IDs it implements at the end of the
  subject line, in the remote branch's style: `(R-IOS-04)`, or `(R-IOS-12, R-IOS-08)`.
  Where a task also touches an R3 requirement, name it too (`R-R3-39`).
* **Protocol versions.** Follow the station branch's rule: each new feature gets its own
  capability version in `StationCapabilities` (`<feature>Version`, the pattern of
  `notchControlVersion` and `audioProfileVersion`), and `kSessionProtocolMinor` never
  changes. Where the station must know a client's support before capabilities are sent
  (device authentication, pairing, the takeover question, Setup descriptions), both ends
  declare features in the `hello` `features` object of Task 4. A client never sends a
  message kind or verb the station has not advertised, because an older station ends the
  connection on anything it cannot decode; an older client logs and ignores an unknown
  kind. Older peers see exactly today's wire (golden comparisons where a test exists).
  Supported majors follow D23 and D39 (Task 4).
* **The link document and the conformance suite move with the wire.** A task that adds or
  changes anything on the wire updates `docs/architecture/2026-09-23-station-link-v1.md`,
  `tests/data/link/v1/` and `surface.json` in the same commit, and the conformance
  runners pass on both ends. That document, as merged from `codex/integrate-r2-main`,
  is the authority for the wire: where this plan describes the wire differently, the
  document wins, and an implementer follows it and names the difference in its report
  so the controller corrects the plan. Its Conformance section defines the fixture
  format both runners implement; the phone's runners follow that section, not any
  description of the format in this plan.
* **The transmit safety boundary.** Nothing lets a remote client key the radio outside the
  station's gates: transmit disabled until snapshot-complete; the watchdog; the
  starvation deadline; the time-out; the unkey-confirmed gate; `TxInterlockPolicy`, PA
  protection and SWR gating authoritative at the station. A reconnect, a snapshot replay,
  a path change or a property write never keys. The tasks that touch this boundary are
  flagged in their execution notes for an earlier independent review.
* **Station code** follows `CLAUDE.md` and `CONTRIBUTING.md`: braces on all control flow;
  no raw `new`/`delete` outside Qt parent ownership; `constexpr`, never `#define`, for
  constants; `m_camelCase` members, `kPascalCase` constants, `PascalCase` classes;
  `qCWarning(lc…)` for errors, never exceptions; `Q_OS_*` platform guards. `AppSettings`,
  never `QSettings`; booleans are `"True"` / `"False"`. Core stays GUI-free (`nereusd`
  links NereusCore only). Cross-thread work uses queued signals; no mutex in an audio
  callback; no network or codec work on the DSP callback (R-R3-06); once Tasks 31 and 32
  land, no WDSP call on an event loop (R-R3-39).
* **Operator wording.** Every string a user reads is plain operator English with no
  protocol, grant, budget, capability, session or snapshot jargon, and no source cites
  inside strings (a cite goes in a comment beside the string). Station-side strings pass
  `OperatorWording::isPlain` (`tests/OperatorWording.h`), and the desktop shows Core
  reasons through `src/gui/OperatorReasonText`, as on the station branch; the phone shows
  the Core's reason text as sent. App text matches the spec's §5 and the board's
  pictures. On screen, in both apps, the NereusSDR computer you connect to, update and
  pair with is "the Core" (D43); "station" appears on screen only in its ham sense (your
  station, the station callsign, the station's network). Code identifiers, wire names,
  the link document and this plan's prose keep "station"; where a task quotes on-screen
  text that says "station" for the Core, write "Core".
* **Attribution.** New NereusSDR-original C++ files start with
  `// no-port-check: NereusSDR-original.` Logic ported from Thetis (Task 33's `StopAllTx`
  from `console.cs`, Task 38's time-out from `TimeOutTimerManager.cs`, the display
  computations Task 20 moves, the Setup text and values Tasks 43 to 46 carry) follows
  `docs/attribution/HOW-TO-PORT.md`: the pre-port checklist, each source file's header
  byte for byte (Samphire's dual-licensing statement where the source has it), a
  `docs/attribution/THETIS-PROVENANCE.md` row, inline cites stamped `[v2.10.3.15]`
  (Thetis at `3759d096`), and every author tag preserved. Vendored or fetched libraries
  get a `docs/attribution/<NAME>-PROVENANCE.md` file with the pinned revision, archive
  hash and licence, and their licence text in `packaging/third-party-licenses/`.
* **The app's licence (D4, R-IOS-29).** Everything under `ios/` is NereusSDR-original,
  licensed GPLv3 plus the App Store permission in `ios/LICENSE` (Task 5). No code, no
  data tables and no text from Thetis, WDSP or AetherSDR go into `ios/`. Anything the
  desktop computes with ported code is computed by the station and reaches the phone as
  data; the phone displays station-supplied text (labels, tooltips) at run time but
  contains none. Third-party code bundled in the app is BSD, MIT, ISC, Apache-2.0 or
  MPL-2.0, with its notice on the licences screen. Conformance fixtures stay in
  `tests/data/link/` and are never bundled into the app; app test fixtures that stand in
  for Setup descriptions are synthetic.
* **Swift code** uses the Swift 6 language mode with strict concurrency, one primary type
  per file, and swift-testing (`import Testing`) for every test. Each Swift file starts
  with the two-line header of Task 5.
* **Commits:** GPG-signed, never `--no-gpg-sign`; no `Co-Authored-By` trailer; no em-dash
  (U+2014) in commit messages, documents or PR text. Stage explicit paths only.
* **Station tests** are built per target and run offscreen, never on screen:
  `cmake --build build --target tst_<name> && QT_QPA_PLATFORM=offscreen ctest --test-dir build -R '^tst_<name>$' --output-on-failure`.
  The build directory is configured once with
  `cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo -DNEREUS_BUILD_TESTS=ON`.
  Read `docs/development/fast-test-loop.md` before any broad run; never run the unfiltered
  suite while iterating. New tests register with `nereus_add_test(tst_<name> …)` in
  `tests/CMakeLists.txt`; session tests add `fakes/LoopbackTransport.cpp`. Timing uses
  injected clocks, never sleeps.
* **App tests** run with `ios/scripts/swift-test.sh` (Task 5), which adds the
  command-line-tools flags when `xcode-select -p` points at the command line tools; the
  cross-implementation tests run with `ios/scripts/interop-test.sh` (Task 10). From Task 51
  on, app targets also build and test with
  `xcodebuild -project ios/NereusSDR.xcodeproj -scheme NereusSDR -destination 'platform=iOS Simulator,name=iPhone 17' test`
  after `ios/scripts/generate-project.sh`.
* **Secrets** never appear in the plan, the source, test fixtures, logs or support
  bundles: no tokens, private keys, pairing codes or device keys. Keys and codes in tests
  are generated at run time. A pairing code appears only on the station's console output
  and its status page, never through the logging categories.
* **Devices** (the radios, the station computers, iPhones and iPads, the website's server)
  are touched only by the controller or JJ, never by an implementer on its own
  initiative. Confirm which device answers before writing to it; never restart or reflash
  a box that could drop off its network without asking. Hardware and device evidence
  stays **pending** until a device shows it.

## Decisions settled in this plan

Each follows from the spec, the designs or the code; none reopens a decision of JJ's.

* **The station listens on TCP 47910 on every interface by default** once identity
  exists (Task 12), beside the existing UDP 47910 announcement; the status page is TCP
  47911 (Task 17). Pairing is what makes the listener safe to expose, and the pairing
  design's first-run workflow (§11) needs it reachable without configuration.
  `remote_port = 0` still turns it off.
* **Device keys are ECDSA P-256** on every client (the phone's lives in the Secure
  Enclave); the station's identity key is P-256 too, and it signs the station's TLS
  certificate so a replaced certificate never breaks a saved station. An upgraded
  station stays claimed through its existing token: each window that signs in with it
  enrols its own key, and the token is retired by an explicit command; a new station
  creates no token (Tasks 12, 13).
* **Remote transmit is allowed for paired devices by default** (`remote_transmit = allow`
  in `nereusd.conf`), since D5 puts transmit in the first release.
* **The transmit numbers:** keepalive 100 ms, link-loss deadline 400 ms, starvation
  250 ms, transmit buffer 60 ms target and 120 ms maximum, first reconnect 1000 ms; the
  per-mode starvation action of Part F, with TUNE and two-tone exempt. Keepalives travel
  on their own unreliable channel on remote paths, key and unkey events are sent three
  times under a keying epoch, and the uplink is rate-matched to the radio's clock
  (Tasks 35 to 37).
* **The time-out applies by device kind** (D29): phones and tablets use new station
  settings, on at 180 s; keying at the station and from computers uses Thetis's own
  settings, off by default. The whole Thetis Time Out Timers group is ported (MOX and
  ping), since a port takes the whole upstream function.
* **No path change while keyed** (Task 29): a path that fails while keyed is covered by
  the watchdog, whose deadline is shorter than the first reconnect.
* **The web-only relay floor is chosen by measurement** (Task 29) among the options the
  App Store app can use: a patched libjuice speaking TURN over TCP and TLS, a local shim
  carrying TURN/UDP to coturn's TLS listener, or our own relay over a WebSocket. libnice
  is excluded because it needs GLib, which is LGPL and cannot go into the App Store app.
  JJ chooses from the measured comparison.
* **The rendezvous service is a small Python service** (Task 26), simpler to deploy and to
  self-host than a Qt build; the C++ and Swift clients run the same conformance vectors.
* **The station's radio choice follows the rules JJ gave the Core/GUI session:** a radio
  chosen from an app first, then the configuration file, automatic only when exactly one
  radio is visible, otherwise the station waits; the desktop manages a remote Core on a
  This Core page (Task 25).
* **The desktop remote window gains microphone transmit** (Task 36), for parity with the
  phone, through the existing capture helper and the microphone chosen in Audio >
  Devices, with the lossless format when the link can carry it; TCI transmit and VOX
  work remotely too (Tasks 35, 36).
* **Spot sources run at the station** (Task 21); a desktop remote window still runs its
  own WSJT-X and SpotCollector listeners for programs on its own computer (remote design
  §6.4).
* **Setup reaches the phone as station-supplied descriptions** (Part H), with a desktop
  parity test and a station live-apply test for every station control described.
* **D41 and D42 apply throughout:** an item the desktop has not built is left out and
  appears once it exists, using the same single list of unbuilt features the desktop
  hides by (R-R3-49); VAX Audio and Antenna Setup are offered from the start; MIDI
  Mapping and Macro Buttons are not built.

# Part C: Identity and pairing

Per the pairing design: the key is the station, each device holds its own key, a
new station is claimed with one tap on its own network or with a speakable code from
anywhere, and revoking a device drops it at once. Identity comes before remote access
and transmit because both depend on knowing which device is which (the takeover report,
the reclaim rule, the time-out by device kind).

**Wire values used by Tasks 12 to 18 (exact):**

* Keys: ECDSA P-256 everywhere (a phone keeps its key in the Secure Enclave). Public keys
  travel as base64url (no padding) of the SubjectPublicKeyInfo DER. Signatures are
  ECDSA P-256 over SHA-256, raw `r || s` (64 bytes), base64url. A key's fingerprint is
  SHA-256 of its SubjectPublicKeyInfo DER; a device's `id` is that fingerprint,
  base64url.
* Certificate binding: the station signs
  `"NereusSDR cert-binding v1\n" || SHA-256(TLS certificate DER)`.
* Device authentication transcript, signed by the device:
  `"NereusSDR device-auth v1\n" || challenge (32 bytes) || SHA-256(TLS certificate DER) || SHA-256(station identity SPKI DER) || SHA-256(device SPKI DER)`.
* The pairing code: `<number>-<word>-<word>`, words from
  `resources/pairing-words-v1.txt`; normalised by lowercasing, trimming, and joining the
  three parts with single hyphens whatever separator was typed.
* SPAKE2+EE identities: client `"nereussdr-device-v1"`, server
  `"nereussdr-station-v1"`; password hashing `crypto_pwhash_OPSLIMIT_INTERACTIVE` and
  `crypto_pwhash_MEMLIMIT_INTERACTIVE`; the confirmation boxes use
  `crypto_aead_xchacha20poly1305_ietf` with the SPAKE shared keys (the client's box with
  `client_sk`, the station's with `server_sk`).
* Files in the station's profile directory, each mode 0600 and written atomically:
  `station-identity.pem` (PKCS#8), `paired-devices.json`.
* The station listens on TCP 47910 on every interface (IPv4 and IPv6) once identity
  exists: pairing is what makes the listener safe to expose, and the pairing design's
  first-run workflow (§11) needs it reachable with no configuration. `remote_port` and
  `remote_bind` still override it; `remote_port = 0` still turns it off.

over UDP first, the web-only fallback required, a separate control connection):

* **A small signalling service plus coturn, on the website's server (D38).** The Python
  service in `rendezvous/` (Task 26) handles registration, introductions and pairing
  mailboxes over a TLS WebSocket on TCP 443, behind the website's Caddy by host name, so

  WebSocket path stays as it is.
* **No path change while keyed.** A background upgrade waits for unkey; a path that
  fails while keyed is covered by the watchdog (Task 37), whose 400 ms deadline is
  shorter than the first reconnect attempt (1 s), which answers the stuck-PTT question
  the pairing design §9.7 left open.

    releases it or disconnects.

    an allocation is refreshed after its credential expired is recorded by a test in
    Docker and decides whether Task 29 refreshes credentials sooner.

# Part F: Remote transmit (R4)

The first store release transmits (D5), so the station gains remote transmit with its
whole safety harness (remote design §12, spec §4.6). It starts with the prerequisite
R-R3-39 names: no DSP call may run on the station's event loop, because every
transmit safety timer runs there. JJ decided on 2026-09-23 that this thread is needed
before remote transmit; no other plan builds it, so this one does.

**Transmit numbers, stated together (remote design §8.3 and §12.3 require it):** a
keyed remote device sends `tx.keepalive` every 100 ms; the station drops transmit 400 ms
after the last one (the link-loss deadline); the microphone starvation deadline is
250 ms; the station's transmit jitter buffer targets 60 ms and never exceeds 120 ms; a
client's first reconnect attempt comes 1000 ms after a loss. So 120 < 250 < 400 < 1000.

**What starvation does, by mode:** LSB, USB, DSB, CWL, CWU, DIGL, DIGU and SPEC stay keyed
through silence (silence there puts no carrier on the air); AM, SAM, FM, DRM, RADE_U and
RADE_L unkey at the starvation deadline (silence there is a bare or garbage carrier).

# Part H: Setup, described by the station

**How the phone gets the desktop's Setup (Tasks 43 to 46, with the display
computations of Task 20).** The desktop's 59 Setup pages are imperative Qt code with
ranges written inline, about 190 tooltips carry Thetis text, and some display behaviours
are Thetis ports. So the station describes each
page as data: `resources/setup/<category>.json`, compiled into NereusCore, served to
clients that declare the `setupDescription` feature, and rendered by the phone
generically (Task 58). The tooltips and ranges travel from the GPL station at run time;
the app contains none of them. A desktop test proves each description matches the real
page, and a station test proves each station setting on it takes effect live.

**The description format (Tasks 43 to 46 write to it; Task 58 renders it):**

```json
{
  "version": 1,
  "category": {"id": "dsp", "title": "DSP", "where": "station"},
  "pages": [{
    "id": "dsp.agcAlc", "title": "AGC/ALC", "where": "station",
    "sections": [{"title": "AGC", "controls": [{
      "id": "dsp.agcAlc.agcSlope",
      "label": "Slope", "tooltip": "<the desktop's tooltip text>",
      "kind": "integer",
      "binding": {"property": {"object": "slice:active", "name": "agcSlope"}},
      "min": 0, "max": 10, "step": 1, "unit": "dB",
      "applies": "live",
      "gate": {"transmit": false}
    }]}]
  }]
}
```

* `kind`: `toggle`, `integer`, `decimal`, `slider`, `choice`, `text`, `colour`, `button`,
  `readout`, `table` (a grid such as the OC pins or per-band PA gain, with `rows`,
  `columns` and a cell kind).
* `binding`: exactly one of `{"setting": "<AppSettings key>"}` (through the settings
  proxy), `{"property": {"object", "name"}}` (a mirrored property), `{"command": {"verb", "arguments"}}`,
  or `{"phone": "<key>"}` (an operator-local setting the phone keeps itself, with the
  description supplying its label, range and default).
* `applies`: `live` for every station-bound control once its task is done; the only
  other value, `subscription`, marks display keys the client puts into its endpoint
  subscriptions (as the desktop's remote window does today,
  `RemoteMediaController.cpp:268-311`).
* `gate`: optional `{"capability": "<name>", "min": N}`, `{"transmit": true}` (greyed
  with the transmit reason until permitted), `{"board": "<capability flag>"}`.
* A page or control the desktop has not built yet is not described, so the phone does
  not show it (D41). The unfinished controls plan's single list of unbuilt features
  (R-R3-49) is the source, the same list the desktop hides by: today General's Startup & Preferences, UI Scale & Theme and
  Navigation (the phone has its own Navigation page, Task 58); DDC Routing; DSP's CW,
  AM/SAM and FM; CAT's Serial Ports, TCP/IP CAT and MIDI Control; Keyboard; all of Meter
  Styles but its one working toggle; Gradients; Diagnostics' Signal Generator and
  Hardware Tests; RX2 Display; the TX grid group. The parity test fails when a page the
  desktop has built has no description and is not on its short desktop-only list (the
  Remote Station page, Skins, Collapsible Display), so a page appears on the phone as
  soon as the desktop builds it and its description is added.
